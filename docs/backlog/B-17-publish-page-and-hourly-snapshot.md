# B-17 — Страница: сборка в gh-pages, снимок раз в час

Два workflow пишут в одну ветку `gh-pages`: сборка wasm на push в `main` и снимок раз в час ([endpoint-snapshot](../api/endpoint-snapshot.md)).

- **Решение и причина.** Общая группа `concurrency` против гонки двух workflow — гипотеза ([исследование, риск 6](../research/research-architecture.md)), проверяется здесь.
- После выкладки — неделя наблюдения за фактическими интервалами расписания (риск 2).

- AC: страница открывается по публичному адресу; `snapshot.json` обновился сам дважды подряд.
- Якоря: `.github/workflows/`.

## Iteration 1 (12.11.2026)

Сделано:

- `.github/workflows/page.yaml` — на push в `main` собирает wasm-страницу и кладёт её в `gh-pages`,
  сохраняя снимок, который там уже лежит.
- `.github/workflows/snapshot.yaml` — раз в час, в :17, `collector --public-only` под `GITHUB_TOKEN`,
  результат — в `snapshot.json` той же ветки.
- `.github/scripts/publish-to-pages.sh` — ветка пишется одним коммитом без истории из её текущего
  дерева; каждый workflow заменяет только своё. Проверено на голом репозитории: страница, снимок,
  снова страница, снова снимок — в ветке один коммит, оба файла свежие.
- `check.yaml` больше не запускается на push в `gh-pages`: иначе каждый снимок гонял бы проверку по
  ветке, в которой нет исходников.

## Вопрос владельцу

Осталось включить GitHub Pages для ветки `gh-pages`. Включить из цикла не удалось: вызов
`POST /repos/youndie/pyatiletka/pages` отклонило автоматическое правило прав, а обходить его цикл не
стал. Варианты:

1. **Включить самим:** Settings → Pages → Source: «Deploy from a branch», ветка `gh-pages`, папка
   `/ (root)`. После этого цикл проверит приёмку: страница по адресу
   `https://youndie.github.io/pyatiletka/` и два подряд обновления `snapshot.json` по расписанию.
2. **Разрешить циклу этот вызов** — тогда он включит Pages сам и проверит приёмку.

Пока Pages выключены, workflow всё равно пишут в `gh-pages`. Ветка в публичном репозитории видна всем:
там только публичные данные, те же, что покажет страница.

## Iteration 3 (13.11.2026)

Находка: расписание не запускается.

| Факт | Где проверено |
|---|---|
| `snapshot` на `main` с 22:46 UTC 12.11, `state: active`, Actions включены, расписание `17 * * * *` — ни одного прогона по `schedule` за четыре слота (22:17…01:17) | `actions/workflows/snapshot.yaml/runs?event=schedule` — `total_count: 0` |
| Тот же файл, запущенный вручную на `main`, отработал: в `gh-pages` снимок 01:28 UTC, 49 репозиториев, все `Public`; Pages пересобрался | прогон 43345069034; `contents/snapshot.json?ref=gh-pages` |

*Гипотеза:* GitHub не прочитал расписание нового workflow, и, по известному его поведению, прочитает
после коммита, который меняет сам файл в ветке по умолчанию. Файл изменён (слот перенесён на :23).
Следующая итерация проверяет прогоны по расписанию. Если их снова не будет, это вопрос: запасной
путь — внешний триггер `workflow_dispatch`.
