# B-17 — Страница: сборка в gh-pages, снимок раз в час

Два workflow пишут в одну ветку `gh-pages`: сборка wasm на push в `main` и снимок раз в час ([endpoint-snapshot](../api/endpoint-snapshot.md)).

- **Решение и причина.** Общая группа `concurrency` против гонки двух workflow — гипотеза ([исследование, риск 6](../research/research-architecture.md)), проверяется здесь.
- После выкладки — неделя наблюдения за фактическими интервалами расписания (риск 2).

- AC: страница открывается по публичному адресу; `snapshot.json` обновился сам дважды подряд.
- Якоря: `.github/workflows/`.

## Вопрос владельцу

Осталось включить GitHub Pages для ветки `gh-pages`. Включить из цикла не удалось: вызов
`POST /repos/youndie/pyatiletka/pages` отклонило автоматическое правило прав, а обходить его цикл не
стал. Варианты:

1. **Включить самим:** Settings → Pages → Source: «Deploy from a branch», ветка `gh-pages`, папка
   `/ (root)`. После этого цикл проверит приёмку: страница по адресу
   `https://youndie.github.io/pyatiletka/` и два подряд обновления `snapshot.json` по расписанию.
2. **Разрешить циклу этот вызов** — тогда он включит Pages сам и проверит приёмку.

Пока Pages выключены, workflow всё равно пишут в `gh-pages`. Ветка в публичном репозитории видна всем:
там только публичные данные, те же, что покажет страница.

## Вопрос владельцу (2)

Чем запускать снимок раз в час? Варианты:

1. **Внешний будильник:** cron на WSL-машине раз в час вызывает `gh workflow run snapshot -R
   youndie/pyatiletka`. Нужен токен с правом `actions: write` на этом репозитории — тот, что уже есть у
   `gh` на машине, или отдельный fine-grained. Интервал выдержан, и всё остаётся в GitHub Actions.
   Минус — зависимость от включённой машины.
2. **Подождать сутки** и посмотреть, заведёт ли GitHub расписание сам: еженедельные проверки в итоге
   пришли. Ничего не стоит, но и не обещает, что прогоны будут раз в час.
3. **Реже и честнее:** снимок раз в 3–6 часов по расписанию и порог `Stale` на вебе — 12 часов. Это
   отказ от «раз в час» из брифа.

Рекомендация — 1, с ручным `workflow_dispatch` до тех пор: он уже работает.

## Вопрос владельцу (3)

Будильнику нужен действующий токен на WSL-машине — цикл его не заводит и не вводит. Варианты:

1. **Отдельный fine-grained токен** (рекомендуется): доступ только к `youndie/pyatiletka`, права
   `Actions: Read and write`. Положить его на машине в файл с правами 600:

   ```bash
   install -d -m 700 ~/.config/pyatiletka && (umask 077; cat > ~/.config/pyatiletka/dispatch-token)
   ```

   (вставить токен, Enter, Ctrl-D). Будильник читает файл сам и нигде токен не печатает. Срок у такого
   токена конечный; когда истечёт, в журнале появится `401`, а веб покажет `Stale` через три часа.
2. **Заново войти в `gh` на машине** (`gh auth login`): будильник возьмёт этот вход, если файла нет.
   Проще, но у такого входа права на все репозитории.

Правило репозитория «токен не пишется на диск» относится к токену доски; у будильника свой токен,
другого назначения, и без файла (или входа `gh`, который тоже лежит на диске) машина без человека
запускать workflow не сможет.

После этого цикл сверит два подряд прогона по `workflow_dispatch` в :07 и `takenAt` снимка и
закроет пункт.
